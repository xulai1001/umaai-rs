# 单局复盘分析（umaai_review）

> 状态：**已实施**（`umaai_review` bin + skill 落地，2026-09-23；§11 步骤 10 发布打包待做）
> 名称已统一为 `umaai_review`（crate / bin / skill；早期草案名 `replay_review` / `umaai-replay-review` 同义）
> 目标：基于 `logs/game{id}.zip` 产出单局复盘（叙事性归因 + 网页版报告）
> 相关：[project_context.md](project_context.md) · [glossary.md](glossary.md) · `archive/handwritten_policy/good_bad_labels_draft.md`（坏手法口径）

## 1. 目标与范围

| | |
|---|---|
| **要做什么** | ① 诊断单局表现（AI / 玩家在哪几回合亏了、亏多少）② 沉淀坏手法标注，供策略迭代 |
| **不做** | 多局对比、育成目标追踪、MCTS 重算（唯一例外是「跨回合反事实」，列为**下一步规划**，见第 13 节） |

## 2. 架构

**Trae Skill（归因层） + 独立 Rust bin（分析引擎）**：计算下沉到 Rust，判断力留给 LLM。

```
logs/game{id}.zip
   │
   ▼  ① umaai_review bin：解包 → 解析 → 派生指标 → 标注 → 渲染
   ├── digest.json    ② 结构化指标（喂 LLM 的上下文包）
   └── report.html    ③ 网页版报告（minijinja 模板 + 内联自绘 SVG，零 JS）
   │
   ▼  ④ .trae/skills/umaai_review/SKILL.md：读 digest.json → 按检查项归因 → 对话输出叙事
Trae Skill
```

| 组件 | 职责 |
|---|---|
| `umaai_review` bin | 解包 / 解析 / 派生指标 / 标注 / 渲染 |
| `templates/report.html.j2` | 报告骨架（**外置**，运行时从文件加载，改样式不重编译） |
| `.trae/skills/umaai_review/SKILL.md` | 归因框架 + 可扩展检查项清单（含通俗化六问叙事） |
| `reference/metrics_glossary.md` | 口径与术语速查 |

**技术选型**：Rust（口径与项目同源、单 exe 零运行时、可复用 `GameStatusRamen` / `record.rs` 口径函数 / `plot/svg.rs`）；
网页用 `minijinja` + 自绘 SVG（零 JS，报告几十 KB）。
**Python 只用于开发期一次性原型**，验证指标定义后即弃，不进仓库。
**无外置配置文件**：剧本机制相关的回合号与阈值一律作为代码常量。

## 3. 分析引擎（Rust bin）

### 3.1 CLI 与产物

```
cargo run --release -p umaai_review -- --zip logs/game421.zip [--out logs/game421/] [--gamedata <path>]
# → logs/game421/digest.json
# → logs/game421/report.html
```

`--out` 默认 `logs/game{id}/`（局包同级同名目录）。参数解析走 `lexopt`。

### 3.2 依赖

现有依赖全覆盖：`zip` / `serde` / `serde_json` / `csv` / `lexopt` / `dunce` / `anyhow`。
**唯一需新增：`minijinja`**（走 `cargo add`，同步 workspace 依赖）。

### 3.3 复用点

1. **快照解析** —— `protocol::ramen::GameStatusRamen` / `GameStatusBase` 是纯 `Deserialize` 结构，
   复盘只需反序列化取字段，**不调 `into_game()`**，无需构建 `RamenGame`、无需初始化 gamedata。
2. **口径函数** —— `decision::record` 的 `detail_header()` / `build_row()` / `raw_from_display()` /
   `num_col()` / `classify_begin_reason()`。
3. **画图** —— `plot::svg::Svg`（零第三方依赖的 SVG 构建器）。

### 3.4 终局评分

快照里**没有**最终评分（`skillScore` 恒为 0）。终局数据**优先用真机终局帧**
（`game{id}_final.json`，育成结束·点技能前，含全部结局事件与末回合比赛奖励，
2026-09-30 起的独立信道）；缺失时回落末份快照估算（缺结局事件 ≈ -2700）。
`meta.final_source` 标注来源，`criteria` 与简报按来源分流措辞。

评分由 `Uma::calc_score` 同源计算（五维查表 `status_final_score` + PT 折算 +
Hint 折算 + 切者/小切 PT 项加成——切者（能人，状态 7）×1.1 / 小切（勤勉好学，
状态 40）×1.04，2026-10-01 起生效；终局帧无该标志，按末快照 `isQieZhe` /
`isXiaoQie` 代入）。等级换算用 `rank.csv` 同表（`GameConstants::get_rank_name`）。
已学技能分不在任何来源内——**AI 端按实际终局五维与技能点的估算，通常略高于
小黑板实际分**（PT 折算高于实际买技能的得分，用户口径 2026-10-07）。

五维评分表自 2026-10-06 起改用 URA `StatusToPoint` 权威表展开
（`gamedata/constants.json` 的 `five_status_final_score`，长度 3802）。

## 4. 归因层（SKILL.md）

### 4.1 检查项机制

归因框架 = **一组可扩展的检查项**，每项统一格式：

```
### <检查项名>
- 判据：<什么情况算命中>
- 取数：<读 digest.json 的哪些字段>
- 输出：<结论格式 / 表格列>
- 状态：<已实现 / 待实测调整>
```

后续检查项按同一格式追加，不动框架。

### 4.2 输出形态

- **叙事归因结论**：只在对话里输出，不落盘
- **网页版报告**：bin 生成 `report.html`，对话中给出路径

## 5. 输入契约

### 5.1 包内布局

`logs/game{id}.zip` 有两种布局：带 `game{id}/` 外壳（旧样例）与不带外壳（当前 `zip_export.rs` 产出）。
**一律按 basename 正则匹配，忽略目录层级。**

| 模式 | 角色 |
|---|---|
| `game(\d+)_turn(\d+)(?:_(\d+))?\.json` | 快照 |
| `game(\d+)_unparsed_(\d+)\.json` | 解析失败快照 |
| `decisions.csv` / `meta.json` / `luck_trend.svg` | 固定角色 |

`decisions.csv` **按表头名取值**，不硬编码列序。`meta.json` 缺失时从文件名与 CSV 降级推导。

**字段命名差异**：`baseGame` 段是 camelCase，`ramen` 段是 snake_case（协议约定，解析时勿混）。

### 5.2 快照里没有的字段

| 缺失项 | 处理 |
|---|---|
| `eat_count` / `yearly_scenario_pt` / `yearly_friend_turns` | 从决策链路派生（统计「吃面」次数、按 `turn` 分年） |
| 最终评分 | 自行计算（见 3.4） |
| **继承属性** | 未记录；只能靠继承回合前后的属性差反推（见 6.4） |
| `absent_cards`（人物缺席） | 未直接记录；从 `personDistribution` 反推（见 5.5） |
| 剧本因子 `extra_count` | 未记录，走配置值（见 6.4） |

### 5.3 锚点语义（关键）

| 规则 | 说明 |
|---|---|
| 决策点快照 = **行动前**局面 | 行动结果体现在**下一个 `turn` 更大**的快照 |
| **同回合 `seq` 递增是阶段推进，不是行动结果** | 必须排除，否则大量误报 |
| **同回合多次推荐可能不同** | RamenSelect 阶段是信息不全时的初判，**Train 阶段才是最终执行**；对比「是否被采纳」只能取 Train 阶段 |
| 地区选择是**回合内子决策**，不是回合行动 | 单独处理，不参与「行动结果」推断 |
| 每回合取**最后一份 `outcome=calc` 的快照**作为决策点 | 中间阶段与 **skip 快照**（`decision_kind` 为空）都不作锚点 |

实测：样例中每 `file` 最多 2 行且同 `file` 的行连续出现（`file` 变化次数 = 唯一 `file` 数 = 156，
156 + 47 = 203 行吻合）→ 链长推断可靠。203 行里 47 行是 skip（`stage=Begin` / `decision_kind` 空），
它们正是若干回合「`chosen_desc` 为空」的原因。

### 5.4 实际执行动作推断

用于回答「玩家有没有听 AI、听的是哪一选」。方法：取「回合末 Train 阶段决策点 → 下一回合首份快照」的状态差。

| 实际动作 | 状态签名 |
|---|---|
| 各属性训练 | 对应五维增长（+13~+134）+ `vital` −15~−26（**智训练例外：不耗体力甚至小回复 +5~+20，判定走主增量阈值而非体力负增量**） |
| 休息 | `vital` **+25~+50**，五维不变 |
| 比赛 | `raceHistory` 长度 +1 |
| 友人出行 | `friend_outgoingUsed` +1 |
| 治病 | `isIll` true → false |
| 吃面 / 剧本 | `feeling_stock` / `scenario_pt` / `super_ramen` 变化 |

**粒度限制**：只能识别「动作类别 + 目标属性」。同类候选需再结合 `feeling_stock` / `selected_regions` 区分。

### 5.5 人物缺席（absent）推断

无直接字段，从「人物索引是否出现在 `personDistribution`」反推：

```
persons 索引 0-5 = 6 张训练卡；personDistribution 中还会出现 6/7/8+（理事长/记者/NPC）
某索引不出现在任何训练位 → absent
```

⚠️ 两个坑：`8` 是 **NPC 占位符**（同一训练位里多个 `8` 是多个 NPC，不是重复人物）；
`personDistribution` 可能是**空数组**（与 `selected_regions` 同类问题），解析必须容忍。

## 6. 检查项清单

### 6.1 坏手法清单（以 `good_bad_labels_draft.md` 为基础，**判据待实测调整**）

| 检查项 | 判据方向 |
|---|---|
| **目标赛未跑赢**（已验证） | `races` − `raceHistory` 非空 —— **`raceHistory` 只记跑赢的比赛**（实测 game6234 命中 turn 45）。反向：`raceHistory` − `races` = 额外自选赛 |
| **关键资源过早耗尽**（已验证） | 一次性资源（友人次数）达上限的回合距结束仍远 + 此后出现体力低点（实测 game6234：turn 58 用完 → turn 69 体力跌至 27） |
| 训练与体力健康 | 训练失败；体力长期低（<35 多回合）；体力高（>85）仍休息 |
| 吃面与资源节奏 | 年末 `eat_count<5`；诀窍 / 隐藏风味获得时溢出 |
| 友人完成度 | 出行次数 <5；出门太晚（>16 回合） |
| free_race 比赛 | 自选比赛区间内次数与时机（见 6.3） |
| 状态健康 | **心情掉落后未及时恢复**（见下方）；心情低（<5 持续）；生病未治 |
| 属性溢出 | 五维接近上限仍训练该属性（速位例外） |

> RMJ 达成**不纳入**（用户明确不需要）。

> **归因口径（用户拍板，2026-09-23）**：目标赛未跑赢、超拉期连亏、掉干劲本身均
> 归**运气**而非操作（输赛是随机结果、掉干劲由输赛带来、超拉估值走低是随机
> 落地差）；「掉干劲后未主动恢复」原是连续事件偏差（旧 6.8 偏差②）导致的决策
> 倾向，该偏差 2026-10-01 已修复、新录制缓解，仍作观察项。

**「心情掉落后未及时恢复」**（旧 6.8 偏差②直接推导，**是本清单里第一个已验证的项**）：

```
判据：motivation 下降后 N 回合内（建议 N=3）
      既无恢复动作（普通出行 / 友人出行 / 休息），motivation 也未回升
```

game6234 实测：

```
turn 45  5 -> 4      行动 = 不吃面 / 比赛        ← 全局限唯一一次掉心情
turn 45~49  连续 5 回合无出行/休息，motivation 停在 4
turn 50  4 -> 5      （由事件恢复，非 AI 主动）
```

对应旧 6.8 偏差②的成因：AI 认为"后面的支援卡事件会把心情补回来"，所以不主动恢复。

**训练失败判据**（已实测校正，原「体力腰斩」错误）：正常训练体力消耗是**固定量**（`scenario_ramen.training_basic_value`
给出准确值，随训练等级 −20~−25，与 `max_vital` 无关）；成功训练的对应属性增长实测 +13~+134。
故判据取「跨 `turn` + **五维零增长** + 体力有消耗」，实现时先输出候选清单人工复核。

### 6.2 运气极值回合归因

对 `luck.top_gain` / `top_loss` 里的回合做归因分类：

| 归因来源 | 数据 | 可用性 |
|---|---|---|
| 基础训练分布好 | `personDistribution` 人数 + 羁绊 + `trainLevelCount` + `training_basic_value` | ✅ |
| **吃面分身触发友情训练** | 见 6.5 | ✅ |
| 需决策事件 | `baseGame.story`（事件 Id / 选项 / `SuccessEffectValue`） | ✅ 仅限有事件的回合 |
| **不需决策的好事件** | `isQieZhe` / `isXiaoQie` / `isAiJiao` / `isRefreshMind` 的 **flag 翻转**、`PositiveThinkingCount` / `LuckyCount` 的**计数变化**；加**排除法剩余**（扣除该回合行动预期收益后的属性增量） | ✅ 候选式，需复核 |
| 面 / 地区效果 | `scenario_ramen` 的 `ramen_basic_effect` / `ramen_region_effect` / `finals_effect` | ✅ |

**不纳入归因**：比赛结果（属预期内收益，不算运气）。

⚠️ **口径要点**：`turn_delta = T(n+1) − T(n)` 是**「局面期望终局分」的变化**，不等于「本回合拿了多少属性」。
归因时须区分「期望变了」与「属性涨了」，否则会误读。

**同回合多段 Δ 的处理（重要）**：

同回合可能有多个 `calc` 决策点（RamenSelect / Train / RegionSelect），**每段都会更新运气分**。
实测 32 个多行回合里有 **19 个符号翻转**（占 59%），且模式固定 —— 吃面段与训练段经常反向：

```
turn 25   [+1190.3(吃面/阪神-耐力), −928.6(耐训练)]
turn 35   [ −612.8(吃面/阪神-耐力), +141.5(力训练)]
```

**这是结构性行为，不是异常**：

| 阶段 | `T(n)` 的含义 |
|---|---|
| 吃面段 | 分身的**叠加态/均分**预期 → 通常比上回合高（正跳） |
| 训练段（吃面后） | 分身**落到具体结果**的偏差 |

由此推出三条解读规则：

1. **「回合合计 Δ」是基本观察单位**，单看某一行的 `turn_delta` 会严重误导
2. **吃面段 Δ > 0** = 分身叠加态带来的均分提升（通常成立）
3. **吃面后的 Δ 符号 = 落地质量**（关键判读）：
   - 继续**大幅正跳** → 落到了**好局面**（彩圈增加、羁绊跨 80 等）
   - **回落** → 落到比均分差的结果

   ➜ 所以 **「吃面段正 + 训练段继续正」是好局面的标志**；只看"两段反向"就下结论是错的

### 6.3 赛程与自由比赛

`gamedata/umaDB.json` 提供赛程信息：

| 字段 | 含义 | 注意 |
|---|---|---|
| `races` | **必赛回合列表** | `[11,28,41,52,59,66,67]` 形态 |
| `freeRaces` | **自由比赛区间 + 要求次数** | **三种形态**：`null` / 对象 / 数组（多区间）；解析必须全部容忍 |

可做：定位自由比赛区间、统计区间内自选比赛（`raceHistory` − `races`）的回合分布与次数、与训练冲突分析。
不可做：评价「该选哪一场」（**比赛池**不在 gamedata）。`preferRaces` / `preferReds` / `bonusData` 当前为空，不可依赖。

### 6.4 继承质量

继承是影响玩家**局外选择**（选哪个继承、养哪个马娘）的重要因素，**单独成节** —— 见第 7 节。

### 6.5 分身触发友情训练（彩圈）

#### 6.5.1 识别判据（已验证）

```
① 快照 cardId 是 idrank（cardId×10 + 突破等级）→ //10 再查 cardDB
② cardDB.cardType：0=速 1=耐 2=力 3=根 4=智 5=友人
③ 训练位索引 0-4 同序：速/耐/力/根/智
④ 分身 = 同一人物索引出现在【不同】训练位（同一训练位内不会重复人物）
⑤ 彩圈 = 分身的 cardType == **分身新增落位**（末快照位置 − 本体位）——**本体占的
   得意位不算**（实测任意位口径的命中大部分是本体占位假象：16 个「命中」里
   14 个是本体占位，分身真实落得意位仅 2/31）
⑥ absent 人物经分身规则出现在场，同属此列
⑦ 有效增加彩圈的**来源二分**（用户拍板）：吃面前本体在场 = 「随机有效增加」
   归**好运气**；吃面前本体缺席（被地区/超拉规则带入得意位）= 「规则有效增加」
   归**好策略**
```

**只统计「吃面后新增的分身」**：同一回合内，比较吃面前（首个快照）与吃面后（末个快照）
的 `personDistribution`，取「该卡位从 ≤1 次变为 ≥2 次」的那些。

实测样例（turn 74）：

```
卡1(速卡) 分身落在[速,耐]位  ★彩圈
卡4(速卡) 分身落在[速,根]位  ★彩圈
卡2(智卡) 分身落在[耐,根]位       ← 有分身但无彩圈
```

#### 6.5.2 必须按两类分开讨论（**关键**）

两类分身的机制与预期完全不同，混在一起统计会**双重失真**：

| | **A. 地区分身**（`turn < 72`） | **B. 超级拉面分身**（`turn ≥ 72`，**只统计训练卡**——友人 cardType=5 无得意位） |
|---|---|---|
| 来源 | 地区加成带来的分身 | `finals_effect` 的 `clone_count` |
| 每回合分身密度 | **1.6 个**（实测 game6234） | **4.7 个**（约 3 倍） |
| 分身落得意位命中率 | 任意位口径 52%（本体占位假象为主）；**分身落位口径 2/31** | 任意位口径 100%；**分身落位口径 1/14——「机制保证」的旧说法基于任意位口径，不成立** |
| 性质 | 真正的随机运气 | 落位为机制行为；盈亏仍只能用该期运气分判 |

#### 6.5.3 B 类（超级拉面分身）的评判

**只能用「该期运气分」判断赚亏**：

- 超级拉面期每回合会新增 4~5 个彩圈，但**玩家本身只能选择一个训练**
- 因此「没吃到新彩圈」**不一定是亏**（约束使然）
- 判据 = 超级拉面期 `turn_delta` 合计的正负

实测 game6234：命中率 100%、每回合都练到了某个彩圈位，**但该期运气分为 −1482 → 判亏**。

#### 6.5.4 A 类（地区分身）的评判

> ⚠️ **判据待精确定义（后续实现阶段标定）**。
> 曾试过「落得意位命中率 + 命中后是否被训练」这套判据，**不准确**，不能作为定稿口径。
> 需要考虑的因素至少包括：该位是否已触顶、是否属于合理补短板权衡、以及如何与运气分挂钩。
> 实测观察值仅作参考基线，勿当判据。

#### 6.5.5 实测基线（game6234，分身落位口径）

| 类别 | 新增分身 | 落得意位（真彩圈） | 被训练 | 随机（好运气）/ 规则（好策略） |
|---|---|---|---|---|
| A 地区分身 | 31 | 2（均在 turn 46：青春永驻→智位、杏目→速位） | 1 | 2 / 0 |
| B 超级拉面分身（训练卡） | 14 | 1（turn 72：青春永驻→智位） | 1 | 1 / 0 |

> 历史基线（任意位口径：A 16/31、B 14/14）保留作对照——其中 14/16 的「命中」
> 是本体占位假象；**地区分身的主要价值是加人头，不是造彩圈**。

**另一个增强情形（第一年常见）**：羁绊刚跨过 80 会**解锁**该卡的友情训练能力，此时若分身又落在匹配位，等于双重新增彩圈。

```
羁绊跨 80（能力解锁，persons[i].friendship 单调上升）
  + 分身落在匹配 cardType 的训练位（上述判据）
  → 双重新增彩圈（「好局面」）
```

⚠️ 区分**能力**与**实现**：`friendship ≥ 80` 的卡数单调上升，但**实际彩圈数每回合随人头分布波动**
（实测第 1 年彩圈位数在 0~2 之间来回，不单调）。不能只看羁绊就断言"彩圈增加了"。

**评分的锚点是「分身是否创造 / 增强彩圈」，而不是「有没有分身」** —— 实测有分身的快照占 88%（game421：137/156）。

### 6.6 超级拉面期运气

- `ramen.super_ramen` 档位、`finals_effect`（含 `clone_count`）、五维增量

  且每回合只能选一个训练 → **「没吃到彩圈」不算亏，只能用该期运气分判赚亏**
- ⚠️ **turn 72 同时落在年份边界，但此处不排除** —— 实测该回合的份量是实打实的

## 7. 继承质量分析

> **单独成节的原因**：继承是玩家**局外选择**（选哪个继承、养哪匹馬娘）的核心输入，不属于单局操作质量，也不该塞进检查项清单。

### 7.1 数据可得性

快照里**只有 `zhongMaBlueCount`**（种马蓝因子数量），**没有继承因子明细，也没有剧本因子 `extra_count`**。
全量关键字扫描无任何 inherit / factor 字段 → **继承属性无法直接读取，只能靠前后对比反推**。

### 7.2 继承回合

`[30, 54]`（**代码常量**）。与年份边界（`[24, 48, 72]`）**错开 6 回合**，是**独立的未记录事件**，与吃面无关。

### 7.3 参考值与算法

| 项 | 值 |
|---|---|
| 参考值公式 | `Σ(extra_count[0..5]) + 126` |
| `extra_count` 来源 | `game_config.toml [config_override]`（注释：种马额外属性 `[速,耐,力,根,智,技能点]`） |
| 当前配置 | `[0,10,20,40,40]` → Σ五维 = 110 → 参考值 **236** |
| 比较口径 | **只比五维，不含 PT** |

算法：取继承回合前后的五维差，**剥离该回合行动本身的贡献**（训练目标属性的增量）
→ 继承贡献 → 与参考值比较偏差。

### 7.4 实测验证（game6234）

```
turn 29 -> 30   五维Δ=[85,138,26,81,49]  Σ+379   行动=耐训练   继承贡献≈+241   vs 236 → 偏差  +5   ✅
turn 53 -> 54   五维Δ=[316,10,104,1,38]  Σ+469   行动=速训练   继承贡献≈+153   vs 236 → 偏差 −83   ⚠️
```

- **turn 29→30 的 +241 vs 236（偏差仅 +5）是最强证据**：三次独立推断（回合号 / 剥离方法 / 参考值公式）互相印证
- **turn 53→54 偏差 −83 是确实的损失** —— 继承质量本身就偏低，**不是**剥离方法的误差（用户确认）。
  报告应直接按「继承质量偏弱」表述，不要打折

### 7.5 输出

报告中单独一块：两次继承的属性贡献 vs 参考值 → 偏差 → 判断（继承质量偏优 / 正常 / 偏弱）。

| `luck_replay` | 按**记录的**决策序列重放 | 只会顺原路走，不能分叉 |
| `luck_probe` | 整局模拟，可覆盖起始 bonus / rmj / pt | 不从快照中途开始，也不能强制首步 |
| `ramen_player` / `bench_base` | 整局模拟，trainer 自选 | 同上 |

**结论：需新开发一个 bin。**

### 13.3 需要的能力（4 步，其中 3 步可复用）

```
① 从快照重建局面        ← 复用（luck_replay / ramen_turn_inspect 已在用 GameStatusRamen::into_game）
② 强制施加指定候选动作  ← 需新写（枚举候选 → 按索引选中 → apply）
③ 之后交给策略走完      ← 复用（RecommendedRamenTrainer / RamenMctsTrainer）
④ N 次重复 + 配对聚合   ← 思路复用 rest_pair_probe 的 CRN 配对
```

实现骨架直接照 `luck_replay` 改：重放到目标回合后**不再读后续快照**，改由 trainer 自由推进。

### 13.4 接口草案

```
replay_fork --zip logs/game421.zip --turn 30 --branch 1,2
            --runs 20 --seed-base 61444 --policy handwritten
```

### 13.5 三个技术难点

| # | 难点 | 应对 |
|---|---|---|
| 1 | **候选描述 → 动作映射**：CSV 只有渲染后的中文描述，要还原成 `RamenAction` 必须重新枚举 `list_actions()` 并渲染描述做匹配 | 同版本代码下可对上；渲染逻辑变更即失配 → **匹配失败时报错并列出候选，不静默跳过** |
| 2 | **RNG 流无法从快照恢复**：快照只给状态，不给 `rule_master` / `turn_fixed` / `event` / `strategy` 三流位置 | 分叉后只能重新注入种子 |
| 3 | 由此推出：**只能做「分支间配对」，不能与原路配对** | ✅ 分支 A / B 用同一新种子互相配对（CRN，`rest_pair_probe` 已验证）<br>❌ 与记录终局分比 —— 差值混着「选择差异」与「随机差异」，分不开 |

### 13.6 能得到的信息

| # | 信息 | 备注 |
|---|---|---|
| 1 | 选择值多少分（配对差 + 95% CI） | ⚠️ 期望差**包内已有**，这项不是增量 |
| 2 | **风险 / 方差**（分布而非均值） | ✅ 增量 |
| 3 | **差异从哪几个回合拉开**（逐回合轨迹对比） | ✅ 增量 |
| 4 | **顺带校验 AI 估值**：实测配对差 vs 包内 `cand1_score − cand2_score` | ✅ 增量 |

> 若只想要「差多少分」，L1 已足够，**不必建此工具**。建它的理由只有 2 / 3 / 4。

### 13.7 成本与参数建议

| 推进策略 | 单次成本 | 可行性 |
|---|---|---|
| 手写基策（`RecommendedRamenTrainer`） | ~1.3ms/整局 | ✅ 默认档，几百次配对秒级出结果 |
| 生产 MCTS | ~3.4 分钟/局 | ❌ 仅作可选档位（20 次要 1 小时以上） |

### 13.8 语义限制（必须写清，否则会误读结论）

分叉后走的是**基策**，不是「当时 AI 的选择逻辑」。所以得到的是：

> 「如果当时选 cand2，然后**交给某个策略**，结果会怎样」

而不是「如果当时选 cand2，**AI** 会怎么继续走」。

两者不同。若基策与当时 AI 的生产配置（`ramen_search_stages` 等）不一致，差异里还掺了策略差异。

### 13.9 与 L1 的分区约束

重算用**当前代码 + 当前 gamedata**，复盘对象却是**历史记录**。因此：

- **不做自动重算**，只做显式按需命令
- 重算结论必须与 L1 结论**分区展示，不混合** —— 否则变成「用今天的标准审判昨天的决策」
